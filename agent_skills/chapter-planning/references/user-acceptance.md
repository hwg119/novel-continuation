# 用户定向修订验收

只对照用户要求、原规划与候选规划验收。不要另起全面审稿，不要求每幕都改，不制造与本次要求无关的新问题。

先判断用户要求主要涉及内容（事件、选择、阻力、结果、节奏、关系或因果），还是仅涉及名称与表达。内容要求不能仅靠换回目、幕名、加形容词宣布解决；创作性要求允许调整具体事件，而非必须机械保留原情节。反之，只要求改名称时，不强迫改变剧情。

逐项核对实际修改如何回应要求；修订前已有的内容不能算新增成果。修改应有可指出的幕与变化，对修补牵动的时间、人物已知信息和跨幕结果检查是否同步。不要为了制造波折篡改历史，新增情节须有自然入口。评估读者体验，不用“出现某个词”代替实际效果，也不强迫添加固定数量的危机。

输出 JSON：
{"requirement_scope":"content 或 labels","passed":true,"summary":"简短说明落实情况","unresolved":[{"scope":"第几幕或全章","problem":"本次要求尚未落实之处","suggestion":"可执行的补修方向"}]}

只有确实落实且 unresolved 为空时 passed=true。证据不足时说明不能确认，不空泛宣布通过。不要输出分幕正文，不要输出与本次要求无关的增强意见。
